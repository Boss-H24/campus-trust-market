## 首个PR建议：参与者隔离的咨询

1. 新增`database/migrations/004_c_conversations.sql`，建立会话/消息表，`(conversation_id,sender_id,client_message_id)`唯一约束；后续迁移编号先与B协调。
2. 新增`server/conversations/repository.ts`、`service.ts`，在`server/app.ts`注册路由并复用鉴权。创建会话时检查商品与对方，禁止自聊。
3. 每次读取或发送均检查当前用户是否为参与者。先补陌生用户读取/发消息、重复clientMessageId、非法内容用例，再完成接口。
4. 咨询页面前台每3秒增量轮询、退出或隐藏停止；服务端最多返回50条。同步OpenAPI，分页状态在客户端明确处理。

## 后续增量

收藏操作幂等。举报人只能查看自己的举报；管理员处理时检查工单状态并记录理由。监管工作台复用A的认证/商品审核列表，提交该列表的`expectedVersion`，409时刷新后再操作。

举报成立后的扣分通过B的`CreditService.applyEvent`，与工单处理在同一事务中执行，重复处理不重复扣分。下架/冻结/禁用需要服务端规则；卖家提交、订单取消或恢复不得绕过冻结。不要将全体会话暴露给普通用户或无授权管理员页面。

## 验收与展示

- [ ] A/B两个会话相互隔离；重复消息、收藏和工单处理符合幂等约束。
- [ ] 未认证、禁用、陌生用户及普通用户调用监管接口均有测试。
- [ ] 举报成立只扣分一次；冻结商品无法由卖家或订单取消重新上架。
- [ ] A原有认证/商品审核仍能完成，旧审核版本拒绝并提示刷新。
- [ ] 页面、迁移、OpenAPI、监管规则、测试和课堂脚本齐全，CI通过。
