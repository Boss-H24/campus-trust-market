## 二 运行环境与工程实现

小程序使用微信原生页面和事件机制，后端按Controller、Service、Repository分层。页面负责采集输入和展示状态；后端决定权限、所有权、状态流转及数据库写入，防止客户端直接修改业务结果。

| 服务端 | Node.js 24.19.0、TypeScript、Express 5 | HTTP接口、会话、业务规则及异常响应 |
| 数据库 | MySQL 8.4.13、InnoDB、mysql2 | 持久化、事务、行锁及索引；保持8.0兼容 |

![图3-1 前后端分层与持久化结构](ppt-assets/05-architecture.png)

server/app.ts负责路由与鉴权；server/users和server/products分别提供Service与Repository。server/db集中连接池、迁移和事务工具，database/migrations保留已应用的不可变SQL。前端通过miniprogram/utils/api.js发送请求并下载有权限访问的图片。

统一响应为{code, message, data, requestId}，成功code为0；错误使用HTTP状态码及可理解提示。编号按字符串传输，金额以整数分存储和传输，列表默认每页20条。



## 三 登录与学生实名认证

### 3.1 会话与登录方式

课堂演示登录验证本机配置的共同密码，返回随机会话令牌；数据库仅保存令牌摘要，默认7天有效，退出时删除会话。请求封装通过Authorization头携带令牌，401时清理本地登录状态。过期令牌不阻断用户重新登录。

代码同时提供wx.login到服务端code2Session的可配置路径。健康接口返回demoLoginEnabled与wechatLoginEnabled，登录页据此显示可用方式；配置开关只表示有无平台参数，不表示外部联调已成功。当前AppID已设置，AppSecret未配置，课堂演示流程已验收。

### 3.2 学籍校验与审核

用户填写姓名、学号、手机号后，服务端先与虚构演示学籍匹配，检查学号是否已被占用，再加密保存并进入PENDING。管理员可通过或驳回，并记录理由；驳回后允许重新提交。未认证或被禁用用户无法发布商品。

![图3-2 本阶段登录认证与发布资格流程](ppt-assets/06-certification-flow.png)

审核列表返回version，提交审核时必须携带expectedVersion。服务端在事务和行锁内比较版本，陈旧列表返回409，避免管理员使用旧页面批准已修改资料。本人页面展示脱敏学号、姓名与手机号；公开卖家资料不返回学号。

未认证学生可浏览，发布接口会拒绝操作；已认证学生可管理自己的商品，管理员才可调用审核接口。资格和角色判断均在服务端执行，隐藏按钮只是页面引导。



## 四 商品发布与基础审核

发布页分组填写图片、标题、分类、价格、成色和描述。服务端要求标题2至50字、描述非空、价格为非负整数分、1至9张图片；单张不超过5MiB，类型与文件签名必须匹配。发布和图片上传都校验当前用户。

![图3-3 商品发布表单与商品审核队列](ppt-assets/03-publish.png)

![图3-3 商品发布表单与商品审核队列](ppt-assets/04-review.png)

图片上传后先关联上传者，待审商品及图片仅本人和管理员可读；商品审核通过后才公开展示。管理员提交通过或驳回动作时也携带expectedVersion，陈旧审核返回409，操作日志仅记录必要的非敏感元数据。

发布、编辑、重新提交均由服务端决定目标状态。已审核商品被编辑后重新进入待审，防止审核后替换内容；LOCKED、SOLD、FROZEN商品禁止卖家直接修改。下架后公开列表及匿名媒体访问随可见性规则收回。

## 六 隐私保护与异常拦截

### 6.1 敏感数据与访问控制

姓名、学号、手机号使用AES-256-GCM加密，每次使用随机IV及认证标签；学号以独立密钥计算HMAC索引进行唯一性校验。密钥保存在本机配置，代码库只包含模板。公开接口采用白名单输出字段，操作日志不记录敏感原文。

表3-3 隐私与异常防护对应

| 风险 | 已实现措施 | 主要代码 |
|---|---|---|
| 身份泄露 | 加密存储、姓名和电话脱敏、公开卖家不含学号 | server/common/privacy.ts<br>server/users/service.ts |
| 越权操作 | 会话、角色、所有权和状态均在后端检查 | server/app.ts<br>server/products/service.ts |
| 伪装图片 | 限制PNG/JPEG/WebP，核对签名与体积 | server/products/rules.ts |
| 重复发布 | 规范化标题与价格检查，卖家行锁串行化 | server/products/service.ts |
| 恶意内容及高频 | 联系方式/违禁词规则，成功发布5件/分钟 | 商品规则与Service |
| 状态绕过 | 动作表、审核版本、编辑后重审 | 商品规则与审核事务 |

### 6.2 重复发布与并发处理

同一卖家24小时内规范化标题相同且价格相同，视为重复发布。若只先查再写，两个并发请求可能都查到不存在。当前实现先锁定卖家行，在同一事务中完成去重、频率和信誉检查，再写商品、图片关联及日志，失败统一回滚。

```text
处理步骤  按真实实现概括
开始事务 → 锁定卖家行 → 检查资格与频率
检查24小时重复标题及价格 → 写入待审商品与图片关联
写入非敏感日志 → 提交；任一步失败则回滚
```

信誉低于60禁止发布。联系方式检查采用词表和模式匹配，无法识别全部同音字或图中文字，仍需人工审核。订单完成、评价和刷单信誉事件现由 B 的唯一信誉服务处理。

## 十 咨询消息与参与者隔离

已登录用户可以就上架商品咨询卖家，未实名认证用户也可咨询；后端拒绝自聊、不可用商品和禁用账号。会话列表与每次消息读写均检查参与者身份，普通陌生人和非参与管理员不能通过会话接口读取消息。卖家和买家的其他会话相互隔离。

消息正文限制为1至1000个Unicode字符，校验全角归一化后的联系方式、外链、引流话术及平台关键词。发送时按用户行锁统计跨会话频率，再锁定会话并写入消息；同一clientMessageId与同一正文的重试返回原消息，正文改变则返回409，避免消息被静默替换。

![图3-5 C咨询消息与增量轮询流程](ppt-assets/07-c-chat-flow.png)

客户端每次最多读取50条消息，以字符串nextAfterId继续读取，避免bigint转换为数值后的精度丢失。服务端多取1条判断hasMore，有积压时立即续读，否则前台每3秒再次请求。页面隐藏或卸载时停止定时器，在途响应不再更新页面。

网络失败后的发送重试保留原消息标识。发送成功响应不直接推进读取游标，下一轮仍按已读取位置取消息，避免跳过同时到达的对方回复。切换账号时清空旧消息与草稿。上述逻辑已通过页面行为及MySQL测试，图3-5为根据代码绘制的说明图，不是原生运行截图。

## 十一 收藏举报与凭证授权

收藏接口以当前登录用户和商品的唯一键保存记录，重复收藏或取消只产生一次业务效果。列表保留已下架、冻结或卖家禁用的商品，并明确标记不可用；客户端不再跳转到其公开详情，用户仍可取消收藏。

举报对象限商品或用户，后端使用当前登录身份作为举报人，禁止自举报及重复待处理工单。本人查询只返回自己的记录和处理结果，不能通过提交他人reporterId扩大范围。管理员可以开始调查、成立或驳回并关闭工单；调查和关闭需提交expectedVersion，陈旧列表返回409。

![图3-6 C举报处置与信誉事务流程](ppt-assets/08-c-report-flow.png)

管理员仅能在指定举报范围内查阅相关会话：会话双方必须为举报人与被举报人，商品举报还须匹配该商品。每次读取消息记录审计，不提供全体聊天公开查询。管理员不能处理或查阅与自己有关的工单。交易纠纷的凭证授权仍须等待B提供订单依据。

成立举报时，在同一数据库连接内完成工单校验、信誉事件调用、商品或账号处置、工单结果及日志写入。重复处理返回409；任一步失败全部回滚。图3-6中的B信誉服务为待接入依赖，当前缺失时返回503，举报保持原状态，商品和分数均不改变。

## 十二 统一监管工作台与冻结保护

监管工作台继续调用A的学生认证与商品审核接口，提交审核列表中看到的expectedVersion。冲突后刷新列表并保留失败提示，由管理员核对最新数据后重新操作，不能自动换用新版本批准。新增举报、账号、冻结、分类、规则与脱敏日志入口。

表3-8 监管功能与服务端约束

| 功能 | 已实现行为 | 权限或状态约束 |
|---|---|---|
| 账号管理 | 禁用或恢复学生账号 | 禁用删除登录会话；恢复须重新登录；禁止改role和信誉 |
| 冻结与解冻 | 冻结商品或为LOCKED商品增加标志 | 卖家编辑、重提和审核不能绕过；解冻不直接上架 |
| 分类维护 | 新增、改名、启用及停用 | 保留已引用分类和商品，不物理删除分类 |
| 平台规则 | 关键词、三类频率及发布信誉门槛 | 仅白名单键，校验数值范围与版本 |
| 操作日志 | 管理员分页查询固定字段 | 不返回可能含身份原文的details |

监管冻结使用独立的moderation_frozen字段。对非交易锁定商品，冻结后状态为FROZEN；对LOCKED商品，保留订单锁定状态并设置冻结标志。管理员解冻只清除监管标志，FROZEN转为OFF_SHELF，LOCKED仍保持LOCKED。该设计使监管决定不会释放交易锁。

平台默认每分钟消息30条、举报5次、发布5件，发布最低信誉60；管理端变更后按数据库规则生效。A商品保存和发布资格检查已接入这些规则。独立账号管理不替代成立举报的扣分事务，B未接入时不能借账号接口将待处理举报伪记为处理完成。

## 十四 B模块接入与后续验收

C通过server/moderation/credit.ts适配B服务，沿用CreditService.applyEvent方法，参数为当前事务连接及用户、事件、来源和分值。C侧约定导出路径为server/credit/service.ts，事件为REPORT_UPHELD，sourceId为举报ID字符串，delta取CREDIT_RULES.report，当前为负5。新增路径和事件名称待B核对，C不直接修改信誉分。

B的信誉表须以事件类型、来源ID和用户ID建立唯一约束，重复事件不重复计分，并将分数限制在0至100。服务必须复用调用方连接，不另行提交或释放连接。当前未找到B服务时返回CREDIT_SERVICE_UNAVAILABLE，使成立举报整笔回滚；这项失败保护已经验证，正式信誉接入仍待B实现。

订单创建须同时检查商品上架、监管冻结标志和双方资格。取消或退款后恢复商品前，B必须重新读取moderation_frozen及卖家状态；冻结时保持不可售，卖家禁用时不能恢复可售，退款未成功前不能释放交易锁。不能仅凭status不为FROZEN判断商品未被冻结。

双方继续在同一仓库的feature/orders-credit和feature/chat-reports开发。A的PR先经组员复核合入main；一方功能合入后，另一方合并最新main再联调。提前联调可建integration/b-c整合双方分支。公共路由、页面入口、OpenAPI和迁移的合并点已列于docs/handoff/c-to-b.md。
