## 第1页 实现目标与成员分工

展示：A/B/C三列任务或报告表3-1。

讲解约45秒：“本阶段先把公共工程、用户认证和商品流程交付为可独立演示的增量。我们能从登录实名走到发布、审核、检索和下架。订单评价由B继续，咨询举报监管由C继续，接口边界已经说明。”

## 第2页 工程与分层

展示：05-architecture.png。

讲解约50秒：“原生页面只负责交互。Controller检查身份与角色，Service决定业务状态、权限和事务，Repository用参数化SQL访问MySQL。金额使用整数分，接口统一响应并带requestId，便于定位问题。”

## 第3页 认证与隐私

展示：06-certification-flow.png。

讲解约60秒：“课堂使用虚构学籍名单加人工审核。身份字段加密保存，学号用独立HMAC索引查重；公开卖家不返回学号。管理员提交审核版本，陈旧列表会被拒绝，避免旧页面批准新资料。真实微信登录还需AppSecret联调。”

## 第4页 发布与审核

展示：03-publish.png与04-review.png并排。

讲解约70秒：“图片成功上传后先处于私有状态，发布进入待审核。审核通过才能公开；编辑后重新审核。标题、价格、图片体积类型及联系方式都由服务端校验。重复发布在卖家行锁内检查，两个并发相同请求只能成功一个。”

## 第5页 首页与详情

展示：01-home.jpg与02-detail.png并排，可配合原生工具点击筛选。

讲解约60秒：“首页的低价专区、教材和宿舍分类都使用真实接口参数，空结果可以清除条件恢复。图片来源和演示身份有明确标注。详情突出价格、成色和认证信息，卖家敏感字段按规则脱敏。”

## 第6页 验证与交接

展示：报告表3-4，或从测试报告复制为PPT原生表格。

讲解约60秒：“13项单元及页面测试、9组真实MySQL集成、十步原生流程通过。100并发下本机p95为110.95ms，样本212件；这只是当前接口测量，不代表真机生产容量。源码、启动脚本、接口、任务清单与B/C接入包已放在GitHub仓库。”

现场演示可额外留1分钟走“实名审核→发布待审→审核上架→搜索查看→下架”。原生相册回调使用虚构图片，真机相册和平台登录保持单独待验收。不要投屏`.env`或把配置密码写进PPT。

## C部分第1页 咨询与消息留存

展示：07-c-chat-flow.png；条件允许时打开“商品详情→咨询卖家”和“我的→我的咨询”。

讲解约60秒：“咨询由登录用户与商品卖家参与。后端每次检查双方身份，陌生人和非参与管理员也不能读取。发送重试保留同一个消息标识，重复提交只留一条；读取每批最多50条，前台每3秒增量轮询，隐藏或退出停止。”

## C部分第2页 收藏与举报

展示：“我的互动”的咨询、收藏和举报结果入口；后续补真实原生截图。

讲解约50秒：“收藏和取消都幂等；商品下架后仍保留记录并标明不可用。举报使用服务端登录身份，不能代他人举报或查询别人的记录，同一个对象已有待处理举报时不能重复创建工单。”

## C部分第3页 监管处置与事务

展示：08-c-report-flow.png，以及统一监管工作台。

讲解约80秒：“工作台保留A的认证和商品审核版本，并整合举报、账号、分类、规则和日志。成立举报与扣分处置共用事务，失败全部回滚。监管冻结有独立标志，交易锁定和冻结可以并存；解冻不会把商品直接上架，也不解除订单锁。”

## C部分第4页 验证与B接入

展示：报告表3-9及[C→B交接](../../handoff/c-to-b.md)。

讲解约60秒：“本次20项单元和页面测试、20组真实MySQL集成通过，其中包括A原有回归。B正式信誉服务尚待接入，当前缺服务会返回503且完整回滚；测试适配器仅验证C事务。下一步用正式信誉服务验证只扣一次分和订单取消后的冻结保护，再完成C原生截图与全组排练。”
